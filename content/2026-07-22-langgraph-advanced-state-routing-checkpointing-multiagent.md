Once you've built your first LangGraph agent, the real questions start. How does state actually merge across nodes? How does the ReAct loop know when to stop? What does a checkpointer save, and why does it need a thread ID? When do you use `interrupt()` versus compile-time interrupts? And how do you wire multiple agents together without them trampling each other's state? These are the 5 concepts that separate production LangGraph systems from toy demos.

## The 5 Concepts

**1. State Reducers** — By default, when a node returns a value for a state field, it replaces whatever was there before. That's fine for single-assignment fields but wrong for anything accumulative. The fix is a reducer annotation: `Annotated[list, operator.add]` tells LangGraph to merge the old and new values using `old + new` instead of overwriting. Without it, a second node writing to `messages` silently destroys the first node's output. With it, every node's contribution stacks. The built-in `operator.add` covers simple concatenation — lists, strings. You write a custom reducer when your merge logic is more specific: deduplicating entries, keeping only the highest-confidence prediction, merging dictionaries, or tracking the latest timestamp. The rule is straightforward: if more than one node writes to the same field and order or history matters, you need a reducer. If you're just storing a single current value that gets updated in place, the default replacement is fine.

**2. Conditional Edges and the ReAct Loop** — `add_conditional_edges()` routes execution to different nodes based on the current state, evaluated at runtime. The canonical use is the ReAct loop: the LLM node runs, a routing function checks whether the last message contains tool calls, and execution either goes to a ToolNode or to `END`. If tools were called, the ToolNode executes them, appends results to `messages`, and routes back to the LLM. The LLM reasons again with the new information. This continues until the LLM produces a response with no tool calls, at which point the routing function returns `END` and the graph stops. The routing function itself is just a plain Python function that receives state and returns a string matching a node name or `END`. Nothing else changes — the same graph definition handles one-shot responses and multi-step tool use without branching your code.

**3. Checkpointers, thread_id, and Time-Travel** — A checkpointer saves the complete graph state after every node execution: current field values, execution position, node history, pending tasks, metadata. `thread_id` is the key that identifies which execution a checkpoint belongs to. Without it, LangGraph cannot distinguish between user A's conversation and user B's, so every concurrent execution needs its own thread ID. Checkpoint namespaces let you further organize checkpoints into logical buckets — production versus development, different experiment runs — and replay any of them independently. That replay capability is time-travel debugging: instead of rerunning the whole graph, you restore state from a specific checkpoint and continue from there. For where to store checkpoints: `MemorySaver` keeps everything in RAM, starts in milliseconds, and loses everything when the process exits — right for local development and notebooks. A Postgres saver writes to a database, survives restarts and crashes, and supports concurrent users — right for anything running in production or involving long-running agents where losing state is not acceptable.

**4. Runtime Interrupts vs. Static Interrupts** — `interrupt()` pauses graph execution at the point it's called, saves a checkpoint, and suspends the process. The application layer can then present information to a human, collect input, and resume with `Command(resume=...)`. The graph picks up exactly where it stopped — no nodes rerun, no state is lost, no matter how long the pause lasts. This is the mechanism for production human-in-the-loop workflows: payment approvals, medical review steps, legal sign-offs, manager authorizations, collecting a missing field before continuing. Static interrupts — `interrupt_before=["tools"]` or `interrupt_after=["llm"]` set at compile time — are different in purpose. They pause automatically before or after a named node on every execution, without any runtime condition. They're debugging tools: you use them during development to inspect state at a specific graph position before proceeding. The practical split is clean: `interrupt()` with `Command(resume=...)` for production workflows that genuinely need human decisions; static interrupts for development-time inspection and testing.

**5. Multi-Agent Topologies and State Isolation** — LangGraph supports three ways to organize multiple agents. A supervisor topology puts one coordinating agent in control: it receives the task, decides which specialist subgraph handles it, and routes accordingly — straightforward to reason about and right for most enterprise workflows. A hierarchical topology adds levels: a top-level planner delegates to mid-level managers, which delegate to worker agents — suited for large planning problems where tasks decompose naturally across layers. A network topology has no central controller: agents communicate directly with each other, which enables flexible collaboration but makes execution harder to trace. On state sharing: a subgraph has its own state schema, and state is only automatically transferred between parent and child for keys that exist in both schemas. If the parent has `messages` and `user_info`, and the child has `messages` and `documents`, only `messages` crosses the boundary. `user_info` and `documents` stay isolated to their respective graphs. This is intentional — subgraphs need private working state without accidentally interfering with the parent or sibling agents. If you need to pass additional data across that boundary, you do it explicitly, not by hoping the schemas overlap.

## The Pattern That Connects All of This

These five concepts are not independent knobs. Reducers determine whether your state accumulates correctly as nodes collaborate. Conditional edges determine whether your agent loops, branches, or exits. Checkpointers make that state durable so loops can span restarts and human pauses. Interrupts give humans a defined entry point into running graphs. Multi-agent topologies determine how you scope state and responsibility across agents. A production LangGraph system uses all of them: `Annotated` reducers on accumulative fields, a ReAct loop driven by conditional edges, a Postgres checkpointer keyed by thread ID, `interrupt()` at decision points that require human input, and subgraphs scoped so their private state stays private. Get the state schema right first — reducers and isolation boundaries are much harder to retrofit than to design upfront.
