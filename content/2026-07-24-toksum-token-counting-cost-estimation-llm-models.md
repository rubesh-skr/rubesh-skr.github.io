Every AI application eventually hits the same three problems: you don't know how many tokens your text consumes, you can't predict what the API call will cost, and you find out the context limit was exceeded only after the request fails. toksum solves all three. One library, one consistent interface, support for over 300 models across every major provider. Here are the 6 capabilities that matter.

## The 6 Capabilities

**1. Token Counting per Model** — The same text produces different token counts depending on which model you're using. GPT-4 and Claude use different tokenizers, so a sentence like "Hello, world! This is a sample text for token counting" comes out as 13 tokens on GPT-4 and 17 tokens on Claude. Neither count is wrong — they reflect how each provider's tokenizer splits text into units. This is precisely why you cannot hardcode a single token count and reuse it across providers. toksum routes each count request to the correct tokenizer for the specified model, so the number you get back matches what the API will actually charge you for.

**2. TokenCounter Class** — When you're processing many pieces of text against the same model, calling the top-level function repeatedly is wasteful. The `TokenCounter` class lets you instantiate once with a model name and reuse the counter across every text you process. The interface stays identical — call `.count()` on each input — but the model lookup and tokenizer initialization happen only once. For batch processing, document pipelines, or any workflow where the same model handles thousands of inputs, this is the right pattern.

**3. Chat Message Token Counting** — Chat APIs don't just send the message content — they include structured metadata: roles like `system`, `user`, and `assistant` are part of the payload and contribute to the token count. A raw character count of your message text will always underestimate what the API charges. toksum counts chat conversations as the API sees them — role metadata included — so the number reflects the actual billing unit. The same conversation counting 30 tokens on GPT-4 comes out at 33 on Claude, for the same reason raw text counts differ: different tokenizers, different overhead per message format.

**4. Cost Estimation** — This is where token counting becomes financially actionable. Given a piece of text, toksum converts it to tokens and multiplies against the model's pricing for input and output separately. A block of text that resolves to 901 tokens costs approximately $0.027 to send to GPT-4 as input and $0.054 if GPT-4 generates an equivalent-length response. Run the same estimation against Claude and you get $0.020. Against GPT-3.5, $0.0009. These numbers let you make an informed choice about which model fits your budget before you make a single API call — not after you've burned through credits on a model that was twenty times more expensive than necessary for the task.

**5. Model Coverage** — toksum maintains a pricing and tokenizer database for over 300 models. OpenAI's GPT-4, GPT-4 Turbo, and GPT-3.5. Anthropic's Claude, Claude Sonnet, and Claude Haiku. Google's Gemini, Gemini Flash, and Gemini Pro. Meta's Llama 3 and Llama 2. DeepSeek Coder and DeepSeek VL. The value of broad coverage is that you don't need to maintain your own pricing table or figure out which tokenizer each provider uses — that work is already done. When a new model ships and its pricing changes, the library absorbs that update rather than your codebase.

**6. Tokenization Behavior Across Text Types** — Not all text tokenizes the same way. Plain English prose like "the quick brown fox" comes out at roughly 4.4 characters per token — compact and predictable. Code is denser: `import numpy as np` produces 19 tokens for 18 characters because symbols, dots, and keywords each tend to become separate tokens. Numbers like `2024`, `365`, and `23.5°C` tokenize inefficiently. Heavy punctuation — sequences of `!`, `?`, `.` — often tokenizes one character at a time. CamelCase identifiers get split at case boundaries, turning one long variable name into several tokens. Understanding this variation matters for any application that processes mixed input: you can't estimate token count from character count alone, and the ratio shifts significantly based on content type.

## The Problem This Actually Solves

Without token counting in your application, you're operating blind. A user uploads a PDF — you don't know if it fits the model's context window, what it will cost, or whether the API call will succeed. With toksum, that uncertainty collapses: the PDF's text converts to a token count, that count checks against the model's context limit, and a cost estimate tells you what the call will run. If the document is too large, you split it before sending. If the model is too expensive, you route to a cheaper one. If the context fits, you send with confidence. That decision loop — count, check, estimate, decide — is what separates applications that fail silently on large inputs from ones that handle them gracefully. toksum puts all the inputs for that decision in one place.
