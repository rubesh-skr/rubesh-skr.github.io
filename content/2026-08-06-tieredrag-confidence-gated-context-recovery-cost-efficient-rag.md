You have a 100-page PDF. A user asks a question about it. The standard RAG approach reads all 100 pages, sends them to the LLM, and pays the full token cost — even if the answer lives on a single page. At $1 per question and 100,000 questions per month, that's $1.2 million per year. The waste is staggering: 70–80% of real-world questions are simple lookups that need less than 5% of the document. But the system reads 100% every time. TieredRAG fixes this with a simple architectural insight: don't throw away context permanently — put it in a waiting room and bring it back only when needed.

## The 7 Components

**1. The Problem with Current Approaches** — Every existing context pruning method — LLMLingua, Provence, CORAG, Selective Context — treats context reduction as a one-way, irreversible operation. They score document chunks for relevance, keep the top 20% (Set A), and permanently delete the bottom 80% (Set B). This saves cost, but when the answer depends on something in Set B, the system produces a wrong answer with no recovery path. In legal, medical, and financial documents, a 5–10% error rate is unacceptable. The fundamental flaw is treating pruning as deletion rather than deferral.

**2. The Two-Set Split** — TieredRAG begins the same way as pruning methods: score every chunk against the query using a hybrid of BM25 (keyword matching) and dense embeddings (semantic similarity), combined as `0.5 × BM25 + 0.5 × cosine similarity`. Rank all chunks by score. The top 20% become Set A — the essential context sent to the LLM first. The bottom 80% become Set B. The critical difference: Set B is not deleted. It stays in memory as raw text, preserved at full fidelity, waiting in a standby state. No compression, no summarization, no information loss. It simply isn't read yet.

**3. Stage 1 — The Fast Pass** — Send only Set A to a cheap, fast model (GPT-4o-mini). The model generates a draft answer using roughly 20% of the document. Cost: approximately $0.05 per query. For questions like "What is the filing date?" or "What does Section 4 say?" — questions where the answer lives entirely within the highest-scoring chunks — this draft is correct and complete. The system could stop here for 70% of real-world queries and save 95% compared to reading everything.

**4. The Confidence Gate** — But how do you know whether to trust the Stage 1 answer? TieredRAG runs three independent verification signals. Signal one: LLM-as-Judge — ask a small model whether the draft answer is fully supported by the Set A context. Signal two: Self-Consistency — generate the answer twice from the same context and check whether both responses agree. Signal three: Uncertainty Detection — check whether the draft contains hedging phrases like "I need more context" or "not enough information." If all three signals pass, the answer is output immediately. If any single signal fails, the system escalates to Stage 2.

**5. Stage 2 — Context Recovery** — This is the novel contribution. When confidence is low, Set B comes back from the waiting room. Set A and Set B are combined — the full 100 pages — and sent to a strong model (GPT-4o). The strong model generates the final answer with complete context. Cost: approximately $1.05 total for this query (Stage 1 cost plus Stage 2 cost). The answer is correct because nothing was ever permanently discarded. This is not re-retrieval from an external database. The context was already scored, already loaded, already sitting in memory. Recovery is instantaneous.

**6. Why This Is Architecturally New** — Every prior method in the literature treats Set B as disposable. LLMLingua compresses it permanently. Provence prunes sentences irreversibly. CORAG discards chunks below budget. AB-RAG re-retrieves from scratch (a fresh database lookup, not recovery of already-scored context). TieredRAG is the first system to implement deferred loading instead of permanent deletion. The waiting room pattern means that information fidelity is 100% preserved for Set B — not compressed, not approximated, not lost. The only cost is holding raw text in memory, which for a 100-page document is roughly 200KB. Negligible.

**7. The Economics** — The math works because question difficulty follows a power law. Easy questions (70% of traffic) resolve at Stage 1 for $0.05 each. Medium questions (15%) also resolve at Stage 1 because the answer happens to be in the top-scoring chunks. Hard questions (15%) trigger Stage 2 and cost $1.05 each. Weighted average: $0.20 per query. Compare that to NaiveRAG at $1.00 per query or LLMLingua at $0.30 per query. At 100,000 queries per month: NaiveRAG costs $1.2M per year, LLMLingua costs $360K per year, TieredRAG costs $240K per year. The savings over naive are $960K annually. Over LLMLingua, the savings are $120K annually — but with dramatically fewer wrong answers because hard questions get full context instead of truncated context.

## The Confidence Gate in Detail

The three-signal gate deserves closer examination because it's the decision boundary between saving money and getting correct answers. The LLM-as-Judge signal works by presenting the Set A context and the draft answer to a small model and asking: "Is this answer fully supported by the provided context? YES or NO." This catches cases where the draft extrapolates beyond what Set A contains. Self-Consistency works by generating the answer twice with the same context — if the model gives different answers from the same input, confidence is low by definition. Uncertainty Detection is the simplest signal: if the model itself says "I need more context," believe it. The gate fires conservatively — any single failure triggers Stage 2. This means occasional unnecessary escalations (false negatives cost $1.00 extra), but never missed escalations (false positives cost wrong answers). In production, the false escalation rate is tunable by adjusting thresholds, but the default leans toward correctness over savings.

## What Existing Methods Sacrifice

The literature comparison makes the trade-off stark. LLMLingua from Microsoft permanently compresses discarded tokens — once compressed, the original text is irrecoverable. Provence from Naver permanently prunes sentences below a relevance threshold. CORAG permanently discards chunks that exceed a token budget. AB-RAG re-retrieves from an external database, which means the re-retrieval might return different chunks than what was originally scored — it's not recovering the same context, it's starting over. TieredRAG preserves the exact chunks that were scored and deferred. When Stage 2 fires, the LLM sees precisely the same document that NaiveRAG would have seen — identical chunks, identical ordering, identical content. The only difference is that for 70–85% of queries, it never needed to read them.

## Production Considerations

The confidence gate adds latency — three additional small-model calls per query. In practice, these run in parallel and add roughly 200ms to Stage 1 queries. For applications where sub-second latency matters more than cost (real-time chat), you can reduce to a single signal (LLM-as-Judge alone). For applications where correctness dominates (legal research, medical QA), keep all three signals and accept the latency. Set B memory overhead is minimal at document scale: 160 chunks of 256 tokens each is roughly 200KB of raw text. At 1,000 concurrent documents, that's 200MB — well within the memory budget of any production server. The real limitation is the confidence checker's accuracy: if all three signals incorrectly say "YES" when the answer is actually wrong, Set B never fires. For high-stakes domains, you can default to Stage 2 for specific query patterns (comparison queries, negation queries, "all" or "every" queries) that empirically correlate with needing full context.

## The Implementation Pattern

The system is built on four components: a chunk scorer (BM25 + sentence-transformers for dense embeddings), a splitter (top-k percent to Set A, remainder to Set B), a two-stage generator (cheap model for Stage 1, strong model for Stage 2), and a confidence gate (three parallel verification calls). The entire pipeline runs synchronously per query — no async complexity, no external state beyond the document chunks in memory. Dependencies are minimal: sentence-transformers for embeddings, rank-bm25 for sparse scoring, and an OpenAI-compatible API for generation. The architecture is model-agnostic — swap GPT-4o-mini for any cheap model and GPT-4o for any strong model. The scoring layer is provider-independent. The confidence gate works with any model that can answer YES or NO.

## The Principle Behind the Architecture

TieredRAG is built on one insight: discarded context should never be lost forever. Every other optimization in the RAG pipeline — chunking strategies, embedding models, re-ranking, prompt engineering — assumes the context selection is final. TieredRAG makes context selection provisional. The first pass is an educated guess. The confidence gate evaluates whether the guess was good enough. If it wasn't, the system recovers instantly rather than failing silently. This pattern — optimistic execution with gated fallback — applies beyond RAG. Any pipeline that makes irreversible decisions early to save cost can benefit from keeping a recovery path open. The cost of holding deferred context in memory is almost always less than the cost of wrong answers in production.
