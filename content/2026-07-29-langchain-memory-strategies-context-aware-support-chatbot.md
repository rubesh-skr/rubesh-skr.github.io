Title: LangChain Memory Strategies: How Context Management Makes or Breaks Your Chatbot

An LLM does not remember previous messages. Every new request starts from zero unless you explicitly feed conversation history back into the prompt. But conversations grow, token limits don't, and API costs scale linearly with input size. The question isn't whether to manage context — it's how. Three memory strategies exist in LangChain, each with a fundamentally different trade-off between recall accuracy, token efficiency, and cost. Here's what happens when you test all three against the same 7-turn customer support conversation and ask a question that depends on information from the very first message.

## The 3 Strategies

**1. ConversationBufferMemory** — The simplest approach: store the entire conversation verbatim and pass all of it into every new prompt. Nothing is lost, nothing is summarized, nothing is approximated. When the user asks "What was the price limit I mentioned?" seven turns later, the full transcript is in the prompt and the LLM finds "$15" without effort. The cost is obvious: token usage grows without bound. A 50-turn conversation means 50 turns of text in every subsequent request. For short conversations — five to ten exchanges — this is the correct default. For anything longer, you're paying for tokens that contribute nothing to the current answer and eventually you hit the model's context limit outright.

**2. ConversationBufferWindowMemory** — A fixed sliding window that keeps only the last k exchanges and discards everything older. Set k=2 and the model sees only the two most recent human-AI pairs. Token usage stays constant regardless of conversation length — efficient and predictable. The failure mode is equally predictable: any information mentioned before the window is gone. In the support chatbot test, the user's $15 budget constraint was stated in turn one. By turn seven, the window contains only questions about Kindle availability and shipping thresholds. The model hallucinates "$35" — not because it's broken, but because the $15 fact no longer exists in its context. Window memory is appropriate when earlier messages genuinely don't matter: stateless FAQ bots, turn-by-turn command interfaces, or scenarios where each exchange is self-contained.

**3. ConversationSummaryMemory** — Instead of keeping raw messages or discarding them, this strategy uses the LLM itself to maintain a running summary of the conversation. After each exchange, the summary is updated to incorporate new information while staying compact. When the price-limit question arrives at turn seven, the summary still contains "$15" because the summarizer identified it as a key constraint worth preserving. Token usage grows slowly — proportional to the density of important information, not the length of the conversation. The trade-off is that summarization is lossy by design: if the LLM's summarizer decides a detail is unimportant, it's gone. You're also paying for an additional LLM call on every turn to produce the updated summary. For long conversations where historical context matters — multi-session support tickets, advisory workflows, ongoing project discussions — this is the right middle ground.

## The Test That Proves It

The experiment is deliberate. A 7-turn customer support conversation is constructed so that the critical fact — a $15 budget — appears only in the first message and is never repeated. Six more turns discuss reviews, authors, hardcovers, alternative recommendations, Kindle options, and shipping. Then the question: "What was the price limit I mentioned again?" Buffer memory answers correctly because it has everything. Window memory fails because it has only the last two turns. Summary memory answers correctly because a well-written summary retains key constraints regardless of how many turns pass. The same LLM, the same conversation, three different answers — determined entirely by which memory strategy was attached. Memory choice isn't a configuration detail. It's an architectural decision that directly controls whether your chatbot gives correct answers or confident hallucinations.
