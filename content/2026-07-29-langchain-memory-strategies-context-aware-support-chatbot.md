An LLM does not remember previous messages. Every new request starts from zero unless you explicitly feed conversation history back into the prompt. But conversations grow, token limits don't, and API costs scale linearly with input size. The question isn't whether to manage context — it's how. Three memory strategies exist in LangChain, each with a fundamentally different trade-off between recall accuracy, token efficiency, and cost. Here's what happens when you test all three against the same 7-turn customer support conversation and ask a question that depends on information from the very first message.

## The 3 Strategies

**1. ConversationBufferMemory** — The simplest approach: store the entire conversation verbatim and pass all of it into every new prompt. Nothing is lost, nothing is summarized, nothing is approximated. When the user asks "What was the price limit I mentioned?" seven turns later, the full transcript is in the prompt and the LLM finds "$15" without effort. The cost is obvious: token usage grows without bound. A 50-turn conversation means 50 turns of text in every subsequent request. For short conversations — five to ten exchanges — this is the correct default. For anything longer, you're paying for tokens that contribute nothing to the current answer and eventually you hit the model's context limit outright.

**2. ConversationBufferWindowMemory** — A fixed sliding window that keeps only the last k exchanges and discards everything older. Set k=2 and the model sees only the two most recent human-AI pairs. Token usage stays constant regardless of conversation length — efficient and predictable. The failure mode is equally predictable: any information mentioned before the window is gone. In the support chatbot test, the user's $15 budget constraint was stated in turn one. By turn seven, the window contains only questions about Kindle availability and shipping thresholds. The model hallucinates "$35" — not because it's broken, but because the $15 fact no longer exists in its context. Window memory is appropriate when earlier messages genuinely don't matter: stateless FAQ bots, turn-by-turn command interfaces, or scenarios where each exchange is self-contained.

**3. ConversationSummaryMemory** — Instead of keeping raw messages or discarding them, this strategy uses the LLM itself to maintain a running summary of the conversation. After each exchange, the summary is updated to incorporate new information while staying compact. When the price-limit question arrives at turn seven, the summary still contains "$15" because the summarizer identified it as a key constraint worth preserving. Token usage grows slowly — proportional to the density of important information, not the length of the conversation. The trade-off is that summarization is lossy by design: if the LLM's summarizer decides a detail is unimportant, it's gone. You're also paying for an additional LLM call on every turn to produce the updated summary. For long conversations where historical context matters — multi-session support tickets, advisory workflows, ongoing project discussions — this is the right middle ground.

## How Each Memory Looks Internally

Understanding what the LLM actually sees at query time makes the behavior predictable rather than surprising. With Buffer memory at turn seven, the prompt contains the full raw transcript — all seven human messages and all seven AI responses, word for word. The token count is the sum of every message ever exchanged. With Window memory at k=2, the prompt contains exactly four messages: the last two human inputs and the last two AI responses. Everything before that is gone — not compressed, not summarized, just deleted. With Summary memory, the prompt contains a single paragraph: a running summary that the LLM rewrote after each turn. The summary at turn seven might read something like "Customer is looking for a mystery novel under $15. Recommended The Silent Witness at $13.99. Customer asked about reviews, author background, hardcover availability, and received a second recommendation. Currently asking about Kindle and shipping options." That paragraph costs maybe 60 tokens regardless of how long the actual conversation was. The raw transcript of seven turns might cost 400 or more.

## Token Economics in Practice

The difference isn't theoretical — it shows up directly in API bills. Assume each turn averages 50 tokens for the human message and 80 tokens for the AI response. After 20 turns, Buffer memory sends 2,600 tokens of history in every request. After 50 turns, that's 6,500 tokens — before you even count the system prompt or the new question. At GPT-4's input pricing, 50 turns of buffer history costs roughly $0.20 per request just for the context. Window memory at k=2 stays at 260 tokens of history regardless of conversation length — essentially free relative to the model's context window. Summary memory grows, but slowly: a well-maintained summary of 50 turns might be 150 to 300 tokens depending on information density. The economic case for summary memory becomes overwhelming somewhere around 15 to 20 turns, where buffer memory starts consuming a meaningful fraction of your token budget and window memory has already lost critical context.

## When Window Memory Hallucinates

The $35 hallucination in the test is not a random failure — it's a predictable consequence of context loss. The model was asked about a price limit. It had no record of the $15 figure. But it did have context about shipping: the previous turn discussed a $35 free-shipping threshold. The model, unable to say "I don't know" without being explicitly instructed to, grabbed the most numerically relevant figure in its visible context and presented it as the answer. This is the dangerous kind of hallucination — not obviously wrong, not absurd, just subtly incorrect in a way that a user might accept. A hallucination about a $15 versus $35 budget could lead a real customer to miss a book recommendation they could afford. In domains with higher stakes — medical dosages, financial limits, legal thresholds — this same failure pattern becomes genuinely harmful.

## The Persistence Layer

Memory strategies operate in RAM during a session, but production chatbots need conversations to survive process restarts. The project stores every message in SQLite via SQLAlchemy — each row captures the role, content, timestamp, and which memory strategy generated the response. A parallel JSON log captures the full session for debugging and analysis. This separation matters: the database is the system of record for conversation history, while the JSON log is an immutable snapshot of a single run's behavior including the comparison analysis. If you were deploying this to production, the database would back your memory reconstruction on session resume, and the JSON logs would feed your evaluation pipeline to track memory strategy performance over time.

## Choosing a Strategy for Production

The decision framework is straightforward. If your conversations are short and predictable — under 10 turns, single-topic — use Buffer memory. The token overhead is negligible and you get perfect recall with zero complexity. If your conversations are long but each turn is independent of earlier context — command-line interfaces, FAQ lookups, transactional interactions — use Window memory with k sized to cover the relevant lookback. If your conversations are long and earlier context matters — ongoing support tickets, advisory sessions, multi-step workflows where constraints accumulate — use Summary memory. The extra cost of summarization is paid back immediately in correct answers that would otherwise be hallucinated. There's also a fourth option not covered in this test: ConversationSummaryBufferMemory, which keeps recent messages in full and summarizes only the older ones. This hybrid gives you perfect recall for the last few turns while maintaining compressed access to earlier context — often the best of both worlds for production systems.

## The Test That Proves It

The experiment is deliberate. A 7-turn customer support conversation is constructed so that the critical fact — a $15 budget — appears only in the first message and is never repeated. Six more turns discuss reviews, authors, hardcovers, alternative recommendations, Kindle options, and shipping. Then the question: "What was the price limit I mentioned again?" Buffer memory answers correctly because it has everything. Window memory fails because it has only the last two turns. Summary memory answers correctly because a well-written summary retains key constraints regardless of how many turns pass. The same LLM, the same conversation, three different answers — determined entirely by which memory strategy was attached. Memory choice isn't a configuration detail. It's an architectural decision that directly controls whether your chatbot gives correct answers or confident hallucinations.

## Why This Matters Beyond the Demo

Every chatbot in production today has a memory strategy, whether the developer chose it intentionally or inherited a default. The default in most LangChain tutorials is Buffer memory — fine for demos, dangerous at scale. The moment your chatbot handles real users with real conversations that extend beyond a few turns, you need to make this choice deliberately. The architecture of this test — running the same conversation through all three strategies and comparing outputs against a known-answer question — is a pattern you should replicate with your own data before deploying. Build your evaluation set from real conversations where context from early turns matters for later answers. Run all candidate strategies against that set. Measure recall accuracy, token consumption, and latency. The strategy that survives your actual data — not a synthetic benchmark — is the one you ship.
